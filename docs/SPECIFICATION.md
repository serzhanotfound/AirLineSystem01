## 1. Цель и масштаб

Создать понятное учебное Java-приложение, демонстрирующее основы языка, ООП, работу с БД и корректность бронирования при одновременных запросах. Пользователь должен уметь объяснить путь HTTP-запроса, обязанности классов, вычисление цены, транзакцию и проверки.

Одна вымышленная авиакомпания, собственные рейсы между реальными аэропортами, прямой перелёт в одну сторону, один конкретный вылет на заказ, валюта KZT. Все платежи и возвраты симулируются. Интерфейс простой, без требований к коммерческому дизайну.

Основной сценарий: администратор создаёт рейс → клиент ищет рейс → выбирает пассажиров и места → получает временное удержание → оплачивает → получает билеты → при необходимости отменяет пассажиров или проходит check-in.

Не входят: реальные платежи, внешние расписания, email/SMS, пересадки, обратные билеты, обмен на другой рейс, несколько авиакомпаний, валют, налоги, овербукинг, программа лояльности, микросервисы, Kubernetes. Не добавлять интерфейсы и наследование только ради количества.

## 2. Принятые упрощения

1. Все пассажиры имеют возраст не менее 18 лет на местную дату вылета в аэропорту отправления. Покупатель также подтверждает совершеннолетие при регистрации. Покупатель и пассажир — разные сущности.
2. Нет CHILD/INFANT, скидок по возрасту, `linked_adult_id` и правил сопровождения. Поле `PassengerType` с единственным значением не создаём.
3. До 9 взрослых в заказе. У каждого собственное место. Отмена отдельных пассажиров сохраняется, но не требует проверки зависимых детей.
4. Места одного рейса защищены общей блокировкой строки рейса в PostgreSQL. Это ограничивает параллелизм внутри рейса, но значительно упрощает доказательство корректности. Разные рейсы могут обрабатываться независимо.
5. Нет смены борта после публикации рейса. Чтобы использовать другой самолёт, администратор отменяет рейс и создаёт новый.
6. После создания заказа нельзя менять пассажиров, места и выбранные услуги. До оплаты можно отменить заказ и создать новый. После оплаты доступна отмена пассажиров.
7. Внутренние уведомления записываются в той же транзакции, что изменение заказа. Отдельная очередь сообщений не нужна.
8. Ручное управление состояниями рейса администратором; автоматические задачи нужны только для истечения броней и сверки платежей/возвратов.

## 3. Роли и доступ

| Роль | Возможности |
|---|---|
| Гость | Поиск, просмотр рейса и мест, регистрация и вход |
| CUSTOMER | Свои заказы, оплата, отмена, билеты, check-in, уведомления |
| ADMIN | Справочники, самолёты, рейсы, тарифы, перенос/отмена рейса, отчёты |

Администратор не получает неявного права использовать клиентские операции над чужим заказом. Управление отменой рейса — отдельная административная операция. Права и принадлежность проверяет сервис, а не только кнопки интерфейса. Чужой и отсутствующий клиентский заказ возвращают одинаковый 404.

## 4. Стек и архитектура

Java 21 LTS, Spring Boot, Maven Wrapper, Spring MVC, Spring Security, Spring Data JPA, Bean Validation, PostgreSQL, Flyway. Тесты: JUnit, AssertJ, Mockito по необходимости, Testcontainers PostgreSQL, Awaitility для фоновых процессов. Docker Compose для локальной БД; OpenAPI через совместимую версию springdoc.

Точные версии фиксируются на этапе создания каркаса после проверки совместимости и доступности. Зависимости Spring управляются BOM выбранной стабильной версии Spring Boot; отдельно не обновляются до несогласованных последних версий. Версия PostgreSQL фиксируется в Compose и Testcontainers одинаково. Lombok не используется.

Один backend отдаёт API и статические HTML/CSS/JS. Одна БД приложения. В ней же отдельные таблицы симулятора, логически не являющиеся таблицами заказа.

Пакеты по функциям: `account`, `flight`, `search`, `pricing`, `seat`, `booking`, `payment`, `ticket`, `checkin`, `notification`, `report`, `common`. Внутри нужны только действительно используемые controller/service/domain/repository; не создавать пустые уровни.

Обязанности:

- Controller: HTTP, DTO-records, валидация формата, коды ответа.
- Service: бизнес-операция, права, транзакция, координация объектов.
- Domain: состояние и локальные инварианты через `hold`, `confirm`, `cancel` и другие методы.
- Repository: хранение, запросы и получение блокировок.

Доменные объекты одновременно JPA entities: field access, `protected` конструктор без аргументов, enum как STRING, без публичных сеттеров статуса. Коллекции выдаются для чтения. DTO не раскрывают entities. `Money` — неизменяемый value object с BigDecimal и KZT; способ JPA-отображения проверяется на каркасе. `Booking` имеет `@Version`, но версия не заменяет блокировки инвентаря.

## 6. Настройки и границы времени

| Настройка | Правило |
|---|---|
| Удержание | 10 минут от создания заказа |
| Начало оплаты | Остаток удержания ≥ 60 секунд |
| Защита новой оплаты | Не меньше 2 минут от начала первой неразрешённой попытки |
| Пассажиры | От 1 до 9 взрослых |
| Лимит PENDING | Не больше 3 заказов на аккаунт |
| Продажи | Открыты только у SCHEDULED и строго раньше вылета − 60 минут |
| Check-in | От вылета − 24 часа включительно до вылета − 45 минут исключительно |
| Клиентская отмена | Строго раньше вылета − 2 часа |
| Оборот борта | Следующий вылет ≥ предыдущий прилёт + 45 минут |
| Значительный перенос | Абсолютный сдвиг от исходного времени покупки строго больше 3 часов |
| Очистка/сверка | Каждые 30 секунд; корректность не зависит от точного запуска задачи |

Хранение времени: `Instant`/`timestamptz`; календарные даты — `LocalDate`. Поиск за день строит диапазон между началами двух соседних местных дат аэропорта отправления, с учётом его zone ID, а не добавлением 24 часов к UTC.

Для критических транзакций время считывается после получения блокировок через `clock_timestamp()` PostgreSQL и передаётся доменным методам как один `Instant`. Для чистых unit-тестов время передаётся явно/через `Clock`. Изменение Java Clock не изменяет время БД. Интеграционные тесты готовят нужные сроки в тестовых данных. Проверка до дедлайна означает момент авторитетной проверки после блокировки; операция, получившая разрешение тогда, может закоммититься чуть позже. Долгих внешних вызовов внутри транзакции нет.

## 7. Рейсы, расписание и инвентарь

Создание рейса требует разных аэропортов, departure < arrival, будущего времени и существующего борта. Схема мест копируется в `flight_seats`; последующее редактирование шаблона не меняет созданные рейсы.

Занятость борта задаётся полуоткрытым интервалом `[departure, arrival + 45 минут)`. Интервалы всех неотменённых рейсов борта не пересекаются. Предыдущий рейс должен прибывать в аэропорт отправления нового, следующий — вылетать из аэропорта его прибытия. Первый известный рейс не требует моделирования исходной стоянки. Проверки выполняются и при вставке между рейсами, и при переносе, и при отмене: удаление среднего рейса не должно создавать недопустимую цепочку соседей. Для учебной версии такую операцию отклоняем с объяснением; сначала администратор отменяет зависимые последующие рейсы начиная с последнего.

Номер, маршрут и борт опубликованного рейса не меняются. Время можно перенести по разделу 13. Тарифы меняются для новых заказов; снимок старого заказа остаётся прежним. Используемый тариф можно деактивировать для новых продаж, физически удалять используемые записи нельзя. У используемого тарифа нельзя менять кабину и тип, а у созданных FlightSeat — номер, кабину и категорию.

Кабины: ECONOMY, BUSINESS. Категории: STANDARD, EXTRA_LEGROOM, EXIT_ROW. Место соответствует кабине тарифа. Все пассажиры 18+, поэтому дополнительного возрастного правила EXIT_ROW не требуется. Иные медицинские/эксплуатационные ограничения не моделируются.

Блокировать можно только AVAILABLE; HELD и BOOKED нельзя переводить в BLOCKED. Из BLOCKED можно вернуться в AVAILABLE. Продажи закрытого/отменённого рейса запрещены независимо от видимого состояния мест.

## 8. Стоимость и услуги

Цена берётся из `FlightFare` для каждого пассажира, выбранной кабины и BASIC/FLEX. Все пассажиры платят 100% базового тарифа. Цена положительна; все денежные значения имеют максимум две десятичные цифры и помещаются в `numeric(12,2)`; отрицательные суммы и переполнение отклоняются.

Выбранные учебные условия:

| Услуга | BASIC | FLEX |
|---|---|---|
| Ручная кладь | 1 место до 7 кг | 1 место до 7 кг |
| Включённый сдаваемый багаж | Нет | 1 место до 20 кг |
| Дополнительный багаж | 0 или 1 место до 20 кг за 6000 KZT | То же сверх включённого |
| STANDARD | Без доплаты | Без доплаты |
| EXTRA_LEGROOM | +5000 KZT | +5000 KZT |
| EXIT_ROW | +3000 KZT | +3000 KZT |

Эти значения — правила вымышленного проекта, а не нормативы реальных перевозчиков. Массу багажа в аэропорту не моделируем. Стоимости услуг конфигурируются, но для заказа фиксируются в снимке. Тарифы одинаково доступны в обеих кабинах при наличии соответствующей записи FlightFare.

Строки цены: FARE, SEAT_FEE, EXTRA_BAGGAGE. Для каждого пассажира ровно одна строка каждого вида, в том числе нулевая. Суммы округляются HALF_UP до scale 2 на уровне строки; итог заказа — сумма строк. Клиент не передаёт доверенную итоговую цену. При создании отправляет идентификатор тарифа и ожидаемую базовую цену/версию предложения; если предложение изменилось, сервер отвечает 409 и просит подтвердить новую цену, не создавая бронь.

Снимок включает базовую цену, сборы, включённый багаж, тариф, кабину, правила и версию политики возврата, исходное время вылета. Возврат не читает текущую цену из FlightFare.

## 9. Создание и истечение брони

Запрос содержит уникальный `clientRequestId`, flightId, от 1 до 9 пассажиров с именем, фамилией, датой рождения, местом, тарифом и допбагажом. Данные непустые, дата рождения допустима, возраст ≥18. Одинаковые имя + фамилия + дата рождения в запросе запрещены. Нормализация: trim, повторные пробелы сворачиваются, регистр не учитывается; это учебная эвристика, не идентификация человека. Проверка одинакового пассажира между разными заказами не выполняется: она создаёт ложные запреты для однофамильцев.

Один `clientRequestId` уникален в пределах пользователя; нормализованный payload сохраняется как hash. Повтор тех же данных возвращает тот же заказ, даже если его статус изменился. Другие данные с тем же ключом — 409. Это проверяется до требования «заказ должен быть PENDING» и до создания новых записей.

В одной транзакции:

1. Заблокировать пользователя и рейс по общему порядку раздела 16.
2. Проверить идемпотентный повтор; очистить просроченные удержания этого рейса.
3. Авторитетно проверить продажи, взрослый возраст, лимит трёх PENDING, цены и набор мест.
4. Убедиться, что все места существуют, различны, свободны и соответствуют тарифам.
5. Создать Booking PENDING, пассажиров и снимки цен; удержать весь набор мест или ни одного.
6. Сохранить подтверждение создания в notifications и закоммитить.

`holdUntil = createdAt + 10 минут`. Начало оплаты дополнительно проверяет, что продажи ещё открыты. Без оплаты удержание может закончиться после закрытия продаж, но новые продажи это не разрешает.

При начале неразрешённой оплаты `protectedUntil = max(holdUntil, paymentStartedAt + 2 минуты)`. Пока такой платёж существует, именно protectedUntil является эффективным сроком; иначе — holdUntil. Значения обновляются атомарно у заказа и его удерживаемых мест. Платёж с известным отказом больше не даёт продления: возвращаемся к исходному holdUntil, а если он уже прошёл — истекаем сразу. Новая попытка после отказа снова требует ≥60 секунд исходного удержания.

По достижении эффективного срока PENDING становится EXPIRED, все его ACTIVE-пассажиры — EXPIRED, места освобождаются с очисткой текущего booking_id и hold_until. Исторический flight_seat_id у пассажира сохраняется. Старые данные не блокируют новое назначение. PAYMENT PROCESSING может продолжать сверяться без права вернуть место старому заказу.

Просроченный PENDING консервативно учитывается в лимите, пока не переведён в EXPIRED. Перед отказом из-за лимита сервис отдельно запускает очистку просроченных заказов пользователя и повторяет операцию; лимит никогда не превышается. Очистка другого рейса не запускается внутри уже захваченной блокировки текущего рейса.

## 10. Оплата и билет

Клиент передаёт `Idempotency-Key`; сумма берётся из заказа. Повтор ключа проверяется первым. На заказ допускается не более одного PROCESSING и не более одного SUCCEEDED за всё время; после успеха новые попытки запрещены. После FAILED можно повторить с новым ключом по правилам удержания.

Три фазы:

1. Короткая транзакция: права, блокировки, повтор ключа, состояние, сроки, создание PROCESSING и защиты мест; commit.
2. Вызов `PaymentGateway` вне транзакции заказа. У шлюза глобальный UUID Payment.id как ключ. Симулятор сохраняет операцию в своей отдельной транзакции и возвращает стабильный результат для этого UUID.
3. Новая транзакция: получить блокировки и время, сверить шлюз, заказ, рейс и принадлежность всех мест. Записать денежный результат ровно один раз.

Успех подтверждает заказ только если он всё ещё PENDING, защита не истекла, все места принадлежат ему и рейс SCHEDULED. Закрытие продаж само по себе не мешает завершить ранее начатую оплату. Создаются по одному Ticket на пассажира, места становятся BOOKED, сроки удержания очищаются, заказ CONFIRMED.

Если успех обнаружен после истечения/отмены или рейс уже недоступен, заказ не оживает: PENDING завершается EXPIRED/CANCELLED по причине, места освобождаются, успешный платёж фиксируется и создаётся полный возврат оставшейся суммы. Повтор финализации не создаёт второй билет или возврат.

Исключение/тайм-аут не переводит платёж в FAILED. Reconciliation опрашивает шлюз после двух минут и далее каждые 30 секунд. PROCESSING сохраняется до определённого результата. Срок удержания при этом не растёт. Неизвестный результат виден пользователю и администратору.

Симулятор: `charge`, `findCharge`, `refund`, `findRefund`; операции хранятся по глобальному UUID с суммой, результатом и моментом готовности. Учебные сценарии: успех, отказ, задержанный ответ, потерянный ответ после сохранённого успеха. Выбор сценария доступен только в demo/test-профиле и явно помечен. Повтор ключа с другой суммой отвергается. Перезапуск не меняет уже сохранённый результат. Новая операция не может оставаться неизвестной бесконечно при исправной БД симулятора.

## 11. Отмена пассажиров и возврат

PENDING можно отменить только целиком в любой момент до истечения; деньги ещё не подтверждены. Если оплата PROCESSING, отмена освобождает места, но платёж продолжает сверяться. Поздний успех вызывает возврат.

CONFIRMED допускает отмену выбранного непустого набора ACTIVE-пассажиров, принадлежащих этому заказу. Для обычной отмены рейс должен быть SCHEDULED и до вылета больше двух часов. Для отмены по праву значительного переноса действует раздел 13. Весь набор отменяется атомарно. Пока хотя бы один пассажир ACTIVE, заказ остаётся CONFIRMED; после отмены всех — CANCELLED. Повтор отмены уже отменённого пассажира возвращает сохранённый результат, не создавая возврат снова.

| Оставшееся время до текущего вылета | BASIC: возврат FARE | FLEX: возврат FARE |
|---|---|---|
| ≥72 часа | 50% | max(0, FARE − 2000 KZT) |
| ≥24 и <72 часов | 0% | 75% |
| >2 и <24 часов | 0% | 50% |
| ≤2 часов | Обычная отмена закрыта | Обычная отмена закрыта |

SEAT_FEE и EXTRA_BAGGAGE возвращаются полностью при допустимой отмене. Коэффициент применяется отдельно к FARE каждого пассажира с HALF_UP; затем складываются строки. Нулевой возврат сохраняется как результат отмены без обращения в шлюз.

В одной транзакции аннулируются пассажир, билет, check-in и текущее назначение места, сохраняются суммы возврата и уведомление. Неуспешный возврат не восстанавливает билет. Само исполнение возврата — вне этой транзакции.

Сумма COMPLETED и зарезервированных REQUESTED/FAILED возвратов не превышает SUCCEEDED-платёж и долю соответствующего пассажира. FAILED сохраняет резерв: повтор выполняет ту же операцию со старым Refund.id, а не создаёт новую. Повтор с неизвестным результатом сначала делает lookup. Шлюз тоже обеспечивает идемпотентность.

Идемпотентность отмены и регистрации: `Idempotency-Key` в таблице `operation_requests` со scope user + operation + target + key и hash payload. Для отмены набор пассажиров нормализуется по id. Повтор возвращает сохранённый результат; изменённый payload — 409. Ключи не заменяют доменные проверки и уникальные ограничения.

## 12. Отмена рейса

ADMIN может отменить SCHEDULED или BOARDING. При наличии соседних рейсов борта проверяются условия раздела 7. Сначала рейс становится CANCELLED под блокировкой: новые брони/финализации уже не проходят. В учебном масштабе заказы этого рейса отменяются в той же транзакции, по booking.id в возрастающем порядке. Вызовов шлюза здесь нет.

PENDING-заказы отменяются с освобождением мест. Для CONFIRMED аннулируются все оставшиеся ACTIVE-пассажиры, билеты и check-in; создаются возвраты. Платежи PROCESSING проверяются позднее и при успехе также возвращаются.

Отмена авиакомпанией возвращает оставшуюся невозвращённую оплаченную сумму по каждому пассажиру, включая ранее удержанную невозвратную часть при клиентской отмене. Уже зарезервированные возвраты учитываются; второй раз та же сумма не возвращается. Автоматические причины уникальны по payment + passenger + reason. Повтор отмены рейса безопасен.

## 13. Перенос рейса

Только ADMIN, только SCHEDULED, новое время в будущем и минимум за 60 минут; сохраняется длительность полёта, маршрут и борт. Проверяются расписание и непрерывность маршрута. Перенос, который делает кого-либо из ещё ACTIVE-пассажиров младше 18 лет на новую дату, отклоняется. Оплаченные цены не меняются.

PENDING-заказы при переносе отменяются: клиент создаёт новый заказ с новым расписанием. PROCESSING сверяется; поздний успех возвращается. Это предотвращает оплату незаметно изменившегося предложения.

У CONFIRMED исходное время покупки не переписывается. Значительным считается абсолютный сдвиг текущего времени от исходного строго больше трёх часов. Последовательные переносы сравниваются с той же исходной точкой. Как только право возникло, оно не отзывается последующим переносом назад.

Право полного возврата оставшейся оплаченной суммы действует до `min(исходное время, новое время)` и фиксируется в заказе. При следующих переносах срок может только сокращаться. Если срок уже прошёл, новый перенос с активными заказами отклоняется; для такого изменения администратор отменяет рейс. До указанного срока разрешена отмена всех или части ACTIVE-пассажиров по этой причине независимо от обычного cutoff. Ранее отменённые пассажиры не получают нового права из-за последующего переноса; отмена самого рейса обрабатывается по разделу 12.

При переносе аннулируются ранее выданные check-in/посадочные талоны, создаётся уведомление; новую регистрацию клиент проходит в новом окне. Ticket.id сохраняется, отображаемое расписание берётся из текущего рейса с отметкой об изменении.

## 14. Check-in, билеты, уведомления и отчёты

Check-in доступен владельцу для ACTIVE-пассажира CONFIRMED-заказа с ISSUED-билетом, у рейса SCHEDULED или BOARDING и в установленном временном окне. Место уже назначено; автоматического выбора нет. Повтор в пределах той же регистрации возвращает тот же посадочный талон. После VOID вследствие переноса допускается новая запись с новым boardingPassId и новым Idempotency-Key; одновременно активна только одна. Повтор старого ключа возвращает исторический результат с текущей отметкой VOID, а не создаёт новую регистрацию. Отдельный GET возвращает только действующий талон.

Билет — страница/JSON с уникальным номером, пассажиром, маршрутом, местом, тарифом и состоянием. Посадочный талон — отдельная страница с boardingPassId. QR, PDF и посадка через сканер не обязательны; печать браузером допустима.

После ARRIVED действующие билеты получают CLOSED. Это означает завершение рейса, а не доказательство посадки. No-show и фактическая посадка не моделируются. Исторические места остаются BOOKED, пассажиры ACTIVE означают «не отменён и не истёк», а не «сейчас находится в самолёте».

Уведомления: создание заказа, подтверждение оплаты/истечение, отмена, перенос, результат возврата. Изменение и запись уведомления атомарны. У события уникальный ключ, повтор обработки не создаёт дубликат. Пользователь видит свои сообщения и отмечает их прочитанными.

Отчёты ADMIN: список заказов по рейсу и статусу; число занятых/свободных/заблокированных мест; проданные действующие билеты; суммы успешных оплат, завершённых возвратов и разность между ними; отдельно незавершённые платежи и возвраты. Разность называется «получено за вычетом возвратов», не прибылью. Учёт расходов и бухгалтерия не входят.

## 15. Машины состояний

- Flight: SCHEDULED → BOARDING → DEPARTED → ARRIVED; SCHEDULED/BOARDING → CANCELLED. BOARDING не раньше открытия check-in; DEPARTED не раньше departure; ARRIVED не раньше arrival. Переходы назад запрещены.
- FlightSeat: AVAILABLE → HELD → BOOKED; HELD → AVAILABLE при expiry/отмене; BOOKED → AVAILABLE при допустимой отмене; AVAILABLE ↔ BLOCKED. После отмены рейса состояние места не даёт права продажи.
- Booking: PENDING → CONFIRMED/EXPIRED/CANCELLED; CONFIRMED → CANCELLED при отмене всех. Терминальные состояния не оживают.
- BookingPassenger: ACTIVE → CANCELLED/EXPIRED. EXPIRED только для истёкшего PENDING. ACTIVE задаёт активность назначения, не посадку.
- Payment: PROCESSING → SUCCEEDED/FAILED. Неизвестный результат остаётся PROCESSING; терминальный результат не переписывается.
- Refund: REQUESTED → COMPLETED/FAILED; FAILED → REQUESTED для повторного исполнения той же операции; lookup может установить COMPLETED после потерянного ответа.
- Ticket: ISSUED → VOID/CLOSED. VOID не восстанавливается.
- CheckIn: ACTIVE → VOID; после переноса возможна новая ACTIVE-запись.

## 16. Транзакции, блокировки и ограничения БД

Уровень изоляции READ COMMITTED плюс явные блокировки и ограничения. Любое изменение инвентаря сначала блокирует строку Flight через `SELECT … FOR UPDATE`. Нельзя вызвать шлюз, ждать пользователя или делать HTTP внутри такой транзакции.

Общий порядок при необходимости нескольких типов блокировок: User → Aircraft → Flight → Booking → Payment → Refund. Внутри одного типа — id по возрастанию. Пропущенные типы не добираются после более поздних. Управление расписанием берёт Aircraft перед Flight; клиентское создание — User перед Flight; финализация/очистка/отмена — Flight перед Booking. Задачи сначала находят кандидатов без блокировки, затем по одному обрабатывают в этом порядке и заново проверяют состояние. Все bulk-обновления соблюдают то же правило.

Если изменяются несколько рейсов в одной операции, блокируются все затронутые Flight по id после Aircraft; при отмене нескольких зависимых рейсов используются отдельные проверяемые операции. Запрещено захватывать чужой Flight из уже заблокированного Booking. Вычитание лимита pending сериализуется блокировкой User; операции, которые только уменьшают число PENDING, не обязаны её брать.

Минимальный набор таблиц — 15 основных из раздела 5, плюс `operation_requests` и две внутренние таблицы симулятора `simulated_charges`, `simulated_refunds`. Цена учебного упрощения — небольшая сериализация, а не дополнительная распределённая инфраструктура.

Обязательные ограничения:

| Таблица/область | Ограничение |
|---|---|
| users | UNIQUE(normalized_email); BCrypt hash, роль из enum |
| airports, aircraft | UNIQUE(iata_code), UNIQUE(registration) |
| aircraft_seats | UNIQUE(aircraft_id, seat_number) |
| flights | departure < arrival; разные аэропорты; FK на борт и аэропорты |
| flight_fares | UNIQUE(flight_id, cabin, fare_type); положительная цена |
| flight_seats | UNIQUE(flight_id, seat_number), UNIQUE(id, flight_id, cabin) |
| bookings | UNIQUE(reference), UNIQUE(user_id, client_request_id), UNIQUE(id, flight_id) |
| booking_passengers | FK (booking_id, flight_id) → bookings; FK (flight_seat_id, flight_id, cabin) → flight_seats; FK (flight_fare_id, flight_id, cabin, fare_type) → flight_fares |
| Активное место | Частичный UNIQUE(flight_seat_id) WHERE passenger.status='ACTIVE'; отсутствие NULL seat_id |
| booking_price_lines | UNIQUE(passenger_id, kind); amount ≥0; все суммы KZT |
| payments | UNIQUE(booking_id, idempotency_key); UNIQUE(booking_id) WHERE status='PROCESSING'; отдельный UNIQUE(booking_id) WHERE status='SUCCEEDED' |
| refunds | UNIQUE(payment_id, passenger_id, reason); сумма >0; глобальный Refund.id для шлюза |
| tickets | UNIQUE(passenger_id), UNIQUE(ticket_number) |
| check_ins | UNIQUE(boarding_pass_id); частичный UNIQUE(passenger_id) WHERE status='ACTIVE' |
| notifications | UNIQUE(event_key, user_id) |
| operation_requests | UNIQUE(user_id, operation, target_id, request_key); hash и сохранённый результат |
| Симулятор | UNIQUE(operation_id); refund FK на charge; positive amount и защита от превышения оплаты |

Для составных FK на целевых таблицах объявляются соответствующие UNIQUE, включая `(id, flight_id, cabin, fare_type)` у flight_fares. Исторические FK не удаляются каскадно. Принадлежность пассажира и Payment одному Booking для Refund проверяется составными FK `(payment_id, booking_id)` и `(passenger_id, booking_id)` к UNIQUE-парам целевых таблиц.

Согласованность HELD: есть booking_id и hold_until; AVAILABLE/BLOCKED: оба NULL; BOOKED: booking_id задан, hold_until NULL — CHECK в flight_seats. Текущий `(booking_id, flight_id)` ссылается на bookings. Возраст, сумма строк, лимит 3, расписание и денежный резерв — сервисные проверки под установленными блокировками; не заявляем, что обычный CHECK может проверять другие строки/таблицы. Схему создаёт Flyway, Hibernate `ddl-auto=validate`.

## 17. API и ошибки

Префикс `/api`. JSON с ISO-датами, UTC Instant, суммой decimal в строке и currency KZT. Списки ограничены пагинацией (по умолчанию 20, максимум 100). DTO входа и выхода раздельные. Все изменения — POST/PATCH, GET не меняет состояние.

| Метод и маршрут | Назначение |
|---|---|
| POST /auth/register, /auth/login, /auth/logout | Регистрация, сессия, выход |
| GET /auth/me, /auth/csrf | Текущий пользователь, получение CSRF-токена |
| GET /flights?origin=&destination=&date=&passengers=&cabin= | Поиск по местной дате; 1–9 пассажиров |
| GET /flights/{id}, /flights/{id}/seats | Детали, тарифы, доступные места |
| POST /bookings | Создание с clientRequestId |
| GET /bookings, /bookings/{id} | Свои заказы и детали |
| POST /bookings/{id}/payments | Начало/повтор оплаты с Idempotency-Key |
| GET /bookings/{id}/payments, /bookings/{id}/refunds | Результаты и незавершённые операции |
| POST /bookings/{id}/cancel | Отмена целого PENDING или выбранных CONFIRMED-пассажиров |
| GET /bookings/{id}/tickets | Свои билеты |
| POST /bookings/{id}/passengers/{passengerId}/check-in | Регистрация с Idempotency-Key |
| GET /bookings/{id}/passengers/{passengerId}/boarding-pass | Действующий посадочный талон |
| GET /notifications; PATCH /notifications/{id}/read | Уведомления |
| GET/POST /admin/airports, /admin/aircraft | Справочники и борт со схемой |
| GET/POST /admin/flights | Управление вылетами |
| PATCH /admin/flights/{id}/fares | Изменение будущих предложений |
| POST /admin/flights/{id}/reschedule, /cancel, /transition | Перенос, отмена, переход состояния |
| PATCH /admin/flights/{id}/seats/{seatId} | Блокировка/разблокировка места |
| GET /admin/reports/flights/{id}, /admin/reports/payments | Отчёты |

Создание — 201; существующий идемпотентный результат — 200; начатая асинхронная оплата/отмена с незавершённым возвратом — 202 с id и URL получения состояния. Отмена может быть завершена при ещё обрабатываемом возврате; эти состояния показываются отдельно. Ошибки: 400 формат, 401 нет сессии, 403 нет роли/CSRF, 404 нет доступного объекта, 409 место/статус/срок/повтор ключа с другими данными, 422 нарушено правило возраста/маршрута. Единый ProblemDetail с code и fieldErrors без stack trace и SQL.

Точный контракт полей и примеры фиксируются OpenAPI на соответствующем этапе; маршруты выше задают полный функциональный объём, но не означают уже реализованный API.

## 18. Безопасность и интерфейс

Серверная сессия, BCrypt, HttpOnly cookie и SameSite=Lax, CSRF для всех изменяющих запросов, включая аутентификацию. Вход/выход через Spring Security с согласованными обработчиками; не писать собственный механизм хранения паролей. Для локального HTTP `Secure=false` только в local-профиле, для HTTPS `Secure=true`. Первый ADMIN из переменных окружения при отсутствии администратора; секреты не сохраняются в Git и не выводятся в лог. Пример env содержит только имена/безопасные заглушки.

UI: поиск; детали рейса и места; форма взрослых пассажиров; заказ с точным состоянием удержания и оплаты; тестовая оплата; список заказов и билеты; отмена и возвраты; check-in; уведомления; простые административные формы и таблицы отчётов. Скрытие кнопки не заменяет проверку прав на сервере. Вставка пользовательских имён через textContent/экранирование, не через сырой HTML.

Показываем сумму, тариф, услуги и условия отмены до создания заказа. При изменении цены запрашиваем подтверждение. Таймер в браузере информационный, решение принимает backend. Истёкшая бронь не выглядит доступной для оплаты, неизвестная оплата не отображается как отказ, отменённый билет не выглядит действующим.

## 19. Проверки приёмки

Unit: Money, округление, суммы строк, границы 72/24/2 часа, возраст 18 лет и часовые зоны, переходы статусов, вычисление защищённого срока и прав после переноса.

Интеграционные проверки на PostgreSQL:

1. 20 разных покупателей одновременно претендуют на одно место — ровно один PENDING, одно ACTIVE-назначение и одно HELD-место.
2. Пересекающиеся наборы из нескольких мест захватываются целиком или никак, без частичных заказов.
3. Четыре одновременных запроса одного пользователя не создают больше трёх PENDING.
4. Повтор создания с тем же ключом возвращает прежний заказ; изменённые данные отклоняются.
5. Истечение освобождает и место, и ACTIVE-назначение; история сохраняется; другой заказ может получить место.
6. Оплата защищает место до единого дедлайна; поиск, cleanup и захват согласованы.
7. Два разных ключа не создают две неразрешённые оплаты; повтор успешного ключа возвращает успех.
8. Отказ возвращает исходный срок, тайм-аут оставляет PROCESSING; поздний успех не забирает перепроданное место.
9. Отмена одновременно с финализацией даёт допустимое конечное состояние и не больше одного полного возврата.
10. Падение после успеха шлюза до записи результата восстанавливается через lookup, в том числе после перезапуска симулятора.
11. Повтор/сбой возврата не создаёт лишних денег; общая сумма и резервы ограничены оплатой.
12. Частичная отмена сохраняет остальных пассажиров; отмена всех завершает заказ; отмена рейса доплачивает только невозвращённый остаток.
13. Ровно 45 минут оборота разрешены, меньше — нет; вставка/перенос/отмена не ломают маршрут борта.
14. Покупка одновременно с отменой/закрытием рейса не проходит по устаревшей проверке.
15. Чужие заказы/билеты/талоны недоступны; CSRF и роли проверяются.
16. Check-in на границах окна, его повтор, аннулирование при отмене/переносе и повторная регистрация корректны.
17. Последовательные переносы, сохранённое право возврата и перенос через 18-летие обработаны по правилам.

## 20. Определение готовности

Проект готов, когда выполнены этапы DEVELOPMENT_PLAN, обязательные тесты реально прошли, основной сценарий воспроизводится через простой UI, README объясняет запуск на компьютере, а владелец может объяснить выбранные классы и транзакции. Команды, ещё не выполненные в чистой среде, не описываются как проверенные.

Документация и реализация меняются вместе. Новое поведение, влияющее на цену, доступность мест, возвраты или права, сначала отражается в спецификации и проверках. Наличие исходников без понятного объяснения и воспроизводимого запуска не считается завершением учебной задачи.
