## 1. Что мы делаем

Разрабатываем учебный проект **Airline Booking & Management System**. Пользователь — Сержан; объяснения и обсуждение можно вести на русском, названия классов и кода — на английском. Важно не только получить работающую программу, но и понимать её устройство и уметь объяснять код.

Основная система и бизнес-логика должны быть написаны на Java. Интерфейс и оформление могут использовать HTML/CSS/JavaScript. Проект должен естественно демонстрировать классы, инкапсуляцию, абстракцию, интерфейсы, полиморфизм, композицию, enum, коллекции, generics, исключения, работу со временем, БД и конкурентными запросами. Не добавлять наследование и паттерны только ради количества.

Главный пользовательский сценарий: администратор создаёт рейс → клиент ищет рейс → выбирает места → создаёт заказ с временным удержанием → выполняет симулированную оплату → получает билеты. Затем добавляются отмена, возвраты и регистрация на рейс.

## 3. Границы системы из редакции 2

- Одна вымышленная авиакомпания; реальные названия аэропортов, собственные вымышленные рейсы.
- Прямой перелёт в одну сторону: один заказ относится к одному конкретному вылету.
- До 9 пассажиров в заказе, включая младенцев.
- Симулированные платежи и возвраты; валюта KZT.
- Своя БД расписаний, тарифов и доступных мест.
- Реальные платежи, пересадки, билеты туда-обратно, обмен на другой рейс, овербукинг, несколько валют, налоги/сборы и email не входят в v1.
- Внешний источник расписаний возможен позже через FlightSearchProvider. Он не предоставляет автоматически право продавать настоящие билеты; импортированные информационные рейсы нельзя молча считать нашим доступным инвентарём.

Роли: гость ищет рейсы; CUSTOMER управляет своими заказами; ADMIN управляет справочниками, рейсами, тарифами и отчётами.

Аккаунт покупателя и пассажир — разные сущности. Один клиент может купить билеты нескольким людям. Номер рейса и конкретный вылет — разные понятия: DEMO101 в разные даты имеет разную доступность мест.

## 4. Архитектура и инструменты из документа

Один Spring Boot backend и одна PostgreSQL БД, функциональные модули внутри одного приложения. Микросервисы не нужны.

Слои:

- Controller: HTTP, формат входа, DTO и ответ; без бизнес-логики.
- Service: бизнес-операция, проверка прав, координация и границы транзакции.
- Domain: состояние и правила объектов; confirm(), cancel(), hold() вместо публичных сеттеров статуса.
- Repository: чтение/запись и запросы с блокировками.

Функциональные пакеты: account, flight, search, pricing, seat, booking, payment, ticket, checkin, notification, report, common.

Стек документа: Java 21 LTS или новее, Spring Boot, Spring MVC, Spring Security, Spring Data JPA/Hibernate, Bean Validation, PostgreSQL, Flyway, Maven Wrapper, JUnit/AssertJ/Mockito, Testcontainers с PostgreSQL, Awaitility, Docker Compose, springdoc-openapi. Конкретные совместимые версии нужно зафиксировать при создании проекта; не выбирать все последние версии независимо друг от друга.

Frontend: HTML/CSS/JavaScript с fetch, желательно на одном origin с backend. Аутентификация: серверная сессия, cookie HttpOnly/Secure/SameSite, CSRF, BCrypt, роли и проверка владельца в сервисах. Параметры окружения используются для первого администратора; секреты не включать в код.

Доменные классы одновременно JPA entities: field access, protected no-arg constructor, методы переходов, неизменяемый доступ к коллекциям, enum как STRING, DTO как records. Money — value object на BigDecimal и валюте; в документе предложен @Embeddable. У Booking предусмотрен @Version. Lombok не используется. Hibernate ddl-auto=validate; схемой управляет Flyway.

## 6. Бизнес-правила редакции 2

Настройки проекта, не правила реальных авиакомпаний:

| Параметр | Значение документа |
|---|---|
| Удержание мест | 10 минут |
| Минимальный остаток удержания для начала оплаты | 60 секунд |
| Тайм-аут обработки платежа | 2 минуты до сверки |
| Максимум пассажиров | 9 |
| Максимум pending-заказов пользователя | 3 |
| Закрытие продаж | за 60 минут |
| Окно check-in | от 24 часов до 45 минут до вылета |
| Последняя клиентская отмена | за 2 часа |
| Значительный перенос | больше 3 часов, право полного возврата |
| Интервал оборота самолёта | минимум 45 минут |
| Очистка удержаний | каждые 30 секунд |

Кабины ECONOMY/BUSINESS; тарифы BASIC/FLEX; категории мест STANDARD/EXTRA_LEGROOM/EXIT_ROW. Место обязано соответствовать кабине тарифа. У младенца отдельного места нет.

Типы пассажиров определяются по возрасту на дату вылета: ADULT от 12 лет — 100% базового тарифа, CHILD 2–11 — 75%, INFANT до 2 — 10%. Для детей/младенцев нужен взрослый, младенцев не больше взрослых; младенец связан с конкретным взрослым.

Java считает цену на сервере и сохраняет построчный снимок цены/условий. Money: BigDecimal, scale 2, HALF_UP на уровне строки; итог — сумма строк; SQL numeric(12,2). Время: Instant/timestamptz, показ и дата поиска по часовому поясу аэропорта.

Клиентские возвраты: BASIC — 50% тарифа при отмене за 72 часа и более, иначе 0%; FLEX — тариф минус 2000 KZT за 72 часа и более, 75% за 24–72 часа, 50% менее чем за 24 часа до cutoff. Доплата за место и допбагаж возвращаются полностью при разрешённой клиентской отмене. При отмене рейса авиакомпанией — полный возврат. Границы диапазонов и минимальную сумму возврата ещё нужно уточнить.

Отмена по документу возможна на уровне пассажира; при отмене всех пассажиров отменяется заказ. Билет появляется после оплаты, посадочный талон — после check-in.

Статусы:

- Flight: SCHEDULED → BOARDING → DEPARTED → ARRIVED; SCHEDULED/BOARDING → CANCELLED.
- Seat: AVAILABLE → HELD → BOOKED; освобождение при истечении/отмене; AVAILABLE ↔ BLOCKED.
- Booking: PENDING → CONFIRMED/EXPIRED/CANCELLED; CONFIRMED → CANCELLED при отмене всех пассажиров. Терминальные состояния не оживлять.
- Payment: PROCESSING → SUCCEEDED/FAILED.
- Refund: REQUESTED → COMPLETED/FAILED с повтором неудачных операций.

## 8. Нерешённые проблемы последнего ревью

### Критичные для реализации

1. **Оплата против истечения удержания (7.3, 8.3).** Cleanup защищает свежий PROCESSING, но lazy reclaim разрешает забрать любое HELD-место с прошедшим hold_expires_at. Эти правила противоречат друг другу. Нужно одно согласованное правило доступности и эффективного дедлайна для поиска, захвата, платежа и cleanup. Предложение: ограниченное продление защиты при начале оплаты с атомарным обновлением; это пока не утверждённое решение.

2. **ACTIVE-пассажиры истёкшего заказа (5, 8.2, 10).** Частичный UNIQUE(flight_seat_id) WHERE status='ACTIVE' продолжает блокировать место, если изменили только booking/flight_seat. Аналогично мешает индекс дублей пассажира. Нужен явный жизненный цикл активного назначения места и его атомарное освобождение, с сохранением истории.

3. **Разные ключи оплаты (7.3, 8.5).** UNIQUE(booking_id, idempotency_key) не мешает двум PROCESSING с разными ключами. Нужен один неразрешённый платёж на заказ и идемпотентная финализация. Повтор существующего ключа после успешной оплаты должен вернуть результат: сейчас проверка PENDING идёт раньше поиска прежнего платежа. На шлюз должен идти глобально уникальный идентификатор операции. Один ключ с другим payload нельзя молча трактовать как новую операцию.

4. **Успех оплаты после отмены.** Phase C должна учитывать booking/flight/payment/seat вместе. CANCELLED не превращается в CONFIRMED или EXPIRED. Если деньги пришли после отмены, нужен ровно один возврат. Исключение/тайм-аут шлюза не означает доказанный отказ; нужно определить lookup и неизвестный результат, а также поведение симулятора после перезапуска.

5. **Проверки до транзакции (7.2).** Продажи, лимит pending-заказов и изменяемые условия могут поменяться до COMMIT. Нужны авторитетные повторные проверки с подходящими блокировками/ограничениями. Определить порядок блокировки всех связанных сущностей, не только seat ids; проверить совместимость cleanup, cancellation, reclaim и payment finalisation.

6. **Оборот самолёта (8.4).** Интервал [departure−45 мин, arrival+45 мин) требует 90 минут между рейсами, хотя настройка обещает 45. Предлагаемая корректировка — [departure, arrival+45 мин). Непрерывность маршрута проверять с предыдущим и следующим рейсами, включая вставку/перенос.

### Остальные уточнения

- Возврат не может быть отрицательным. Нужен лимит совокупных возвратов относительно оплаченной суммы, включая разные причины и незавершённые запросы. Повтор исполнения возврата в шлюзе должен использовать стабильный ключ.
- Точные составные FK для рейса/кабины/тарифа/места в таблицах ещё не заданы.
- Право бесплатной отмены после переноса: конечный срок, перенос раньше, последовательные переносы, отношение к обычному cutoff.
- Перенос через второй день рождения младенца меняет потребность в месте; правило не определено.
- Имя + дата рождения — упрощённая проверка дублей, а не надёжная идентификация человека.
- USED после вылета не доказывает посадку пассажира; определить смысл статуса или позже добавить no-show/boarding.
- PostgreSQL now() — время начала транзакции, не фактическое время после ожидания lock. Выбрать момент проверки дедлайнов. Фиксация Java Clock не фиксирует часы БД.
- Запись notification из AFTER_COMMIT требует отдельной транзакции. Без сохранённого события уведомление может потеряться при падении процесса; решить, допустим ли best-effort в MVP.

## 9. Тесты и этапы

Ключевые тесты документа: 20 запросов на одно место — один победитель; пересекающиеся наборы мест захватываются целиком или никак; просроченный заказ не получает чужие места; повтор платежа/отмены не создаёт дублей; поздний платёж возвращается; цены и возврат считаются по снимку; пересекающиеся рейсы одного борта не создаются; чужой заказ недоступен; переходы статусов и часовые пояса корректны.

По ревью добавить тесты: защищённое удержание во время оплаты; ACTIVE-назначения после expiry; два разных payment keys; повтор успешного payment key; отмена одновременно с успешной оплатой; восстановление после успешного gateway refund до записи в БД; точная граница оборота 45 минут; захват места одновременно с закрытием/отменой рейса.

План из документа: требования → диаграммы и миграции → ранняя проверка захвата мест на PostgreSQL → доменная логика → платёж и билет → аккаунты/API → интерфейс → отмены/изменения/check-in → уведомления/отчёты/демо.

Помощник предложил уменьшить первый рабочий сценарий до одного взрослого, одной кабины, простого тарифа и отмены целого заказа, затем расширять. **Пользователь это ещё не подтвердил.** Не менять молча итоговый объём. Конкурентность и идемпотентность не откладывать даже в упрощённом сценарии.
